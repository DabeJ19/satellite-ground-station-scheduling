## 阻擋項（必修）

### B1 — 舊版本拖曳混用目前版本，刪除需求後會拋例外

對應：**SPEC §6 甘特圖拖曳、§4.2 版本隔離、§8 S3**。位置：`src/ui.js` 的 `initGanttDrag`、`ganttPointToSlot`、`ensureManual`。

實測輸入／步驟：以預設資料建立 MILP 槽 `[{req:'R1',antenna:'GS_1-S',start:0}]`；提交刪除 R1 的新資料，保持 MILP 槽選取；在仍顯示的舊 R1 區塊 pointerdown。實際拋出 `Cannot read properties of undefined (reading 'durMin')`，且留下 `state.drag`。原因是區塊來自 `slot.norm`，但 `moveDrag` 用 `state.norm.reqById` 取需求。即使 id 仍在，時間換算也使用目前 H，而列與區塊使用舊快照。另有 base 不一致：舊來源的 ghost 以空排程預覽，`ensureManual` 卻可能使用目前版本既有 manual 槽，放下後的違規與預覽不一致。

可直接採用的修正文句：

> 舊 revision 解槽保留檢視與播放，但禁止由該槽的任務或托盤開始拖曳，並顯示「舊版本解，請先切換目前版本手動槽或重新求解」。拖曳保存開始時的 revision；commit 立即清除拖曳與 ghost、移除拖曳樣式，後續舊事件不得寫槽。pointercancel 同樣清除且不提交。需求、天線及目標列皆存在於同一版本才可處理；ghost 和放下共用同一個來源排程解析程序。

補測輸入＋預期：上述刪 R1 反例不拋例外、不建立 manual；把 H 改 80／刪天線後仍不能拖舊槽；已有目前 manual 時，舊槽的拖曳不覆蓋它；目前版本拖曳中 commit 或 pointercancel，之後 pointerup 不產生修改。保留現有「同版本複製後修改、原槽不變」測試。

### B2 — 播放控制列與動畫採不同版本，commit 後滑桿不同步

對應：**SPEC §6 同一時間游標與三解槽播放、§8 S3**。位置：`src/ui.js` 的 `initPlayback`、`setTime`、`startPlay`、`renderSched`、`commit`。

`drawAnim`／`drawGantt` 使用選取槽快照；滑桿換算、clamp、循環 H 與控制列時間則使用 `state.norm`。實測：保留預設 MILP 快照（H=40、timeOrigin=10:00），`setTime(30)` 得滑桿 75%；提交 H=80、timeOrigin=20:00 的新資料後仍選舊 MILP。滑桿仍 75%，控制列改用新 origin；對滑桿送 input 後 t=60、標籤 `21:00`，舊槽 H 仍 40，甘特圖游標消失，播放也要到新 H 才循環。即使沒有舊槽，commit 縮小 H 將 t 重設為 0 時，也沒有同步滑桿值。

可直接採用的修正文句：

> 定義共用的播放資料來源：選取槽存在時取該槽 norm，否則取目前 norm；動畫、甘特圖、滑桿百分比、時間標籤及循環 H 全部使用它。切槽和 commit 後重新 clamp t 並同步滑桿及標籤；commit 暫停播放並清除 rAF／last，重新按播放才以新的時間戳起算。保留舊槽時，標籤及循環沿用舊快照的 origin／H。

補測輸入＋預期：上述 H40→80／origin10:00→20:00，在舊槽滑桿 75% 必須仍是 t=30、`10:30`；切至目前版本空槽後 75% 為 t=60、`21:00`，所有游標一致。無解槽時 t=30／H40，commit H20（搭配全空資料集合）後 t=0、滑桿=0、播放暫停；舊 rAF 不得推進時間。以受控時間戳驗證暫停後重播不累加暫停時長。

### B3 — 格點只細化單一候選，未遵守多解取最小角度

對應：**SPEC §6 相位擬合／多解規則、§8 S3**。位置：`src/anim.js` 的 `fitPhase`。

可重現的合法 fixture：`H=60`、一顆衛星 A、七個站 `G0..G6`，各一支 S 頻段天線、無需求；每站各有 A 的時窗 `[0,60)`；站角度為 `θ_i=(180.1+360i/7) mod 360`，`i=0..6`。所有中點為 30，故目標相位點為 `0.1+360i/7`。七個旋轉等價的最小值分別在這七個角度，最小角度為 **0.1°**。每個解的殘差 RMS 為 `720/7≈102.857142857°`，平方和為 `74057.14285714286`。

實測回傳 **51.529296875°**（RMS 約 102.857142860°）。0.5° 格點對七個等價盆地的取樣誤差不同，先選到較大的角度再只細化該處；現有 90°／270° fixture 恰好都落在格點，沒有測到這件事。

可直接採用的修正文句：

> 保留 0.5° 格點＋固定步長細化，但不得只細化格點最低的一個候選；收集各局部最低盆地（包含 359.5°／0° 交界），逐一細化後比較其 cost。明定細化精度與 cost 等價容差，在等價最小值中取正規化至 [0,360) 後最小的角度；不得以粗格點誤差打破多解排序。

補測輸入＋預期：上述七站 fixture 反覆執行一致，phi 與 0.1° 的圓周距離不超過 0.001°，RMS 誤差不超過 0.001°。另加跨 0° 的單點 fixture，確保邊界細化與角度排序一致。這是修正多解規則，不推翻 PO 已決定的近似搜尋方法。

### B4 — 動畫的 NUL 分隔複合鍵重新引入碰撞，錯誤發光

對應：**SPEC §2 合法 id、§6 接觸狀態以資料為準、§8 S3**。位置：`src/anim.js` 的 `drawFrame`／`visibleSet`。

合法輸入：H=60、兩顆衛星 id 為 `"a\u0000b"`、`"a"`；兩站 id 為 `"c"`、`"b\u0000c"`，各一支不同 id 的 S 天線；唯一 visibility 為 `(sat="a\u0000b",station="c",start=0,end=10)`，無需求。資料驗證通過。在 t=1，`contactState.visible` 正確只回傳該一對，但 `sat+'\u0000'+station` 使這一對與 `(a,b\u0000c)` 同鍵。實測 canvas 呼叫顯示**兩站皆用 accent／shadowBlur=14，兩顆衛星皆 shadowBlur=16**，把不在任何時窗的第二站／第二星也畫成可見。

可直接採用的修正文句：

> `drawFrame` 的可見 pair 索引使用巢狀 Map／Set，或 `JSON.stringify([sat,station])`；禁止以任意 id 可含的分隔字元串接作鍵。站點與衛星的亮起狀態必須只由其實際可見 pair 決定，不額外限制既有合法 id。

補測輸入＋預期：上述 fixture 在 t=1 僅第一站／第一星發光，第二站／第二星保持未接觸狀態；t=10 兩者都不發光。須驗證渲染判定或 canvas 呼叫，僅檢查 `contactState` 回傳陣列抓不到此回歸。

### B5 — 全時域可見時窗被畫成零長度弧

對應：**SPEC §6「時窗內 → 站與軌道段發光」、§8 S3**。位置：`src/anim.js` 的 `drawFrame` 時窗弧端點。

合法輸入：H=60、一星 A、一站 G（angleDeg=0、一支 S 天線）、唯一時窗 A/G `[0,60)`，無需求。t=1 時應整條軌道發光。`satAngle` 分別將 t=0、60 正規化至相同角度，因此實測高亮弧呼叫為 `arc(300,200,176,π/2,π/2)`，長度為 0；只有底下的普通軌道圈，沒有可見弧。這也會發生在多段相鄰時窗正規化合併成 `[0,H)` 後。

可直接採用的修正文句：

> 時窗弧使用未取模的角度跨度：先求起點 a0，再令 a1=a0+ω·(end−start)·π/180；只正規化顯示位置，不正規化時窗弧長。長度 H 的時窗必須畫出 2π 的完整高亮圓，並仍依半開區間控制亮度。

補測輸入＋預期：上述 fixture t=1 的可見弧跨度為 2π、使用高亮 alpha／線寬；t=60 不亮。再測 `[0,30)` 與 `[30,60)` 合併後相同；跨角度 0° 的一般短窗仍保持正確跨度，不變成補弧。

### A1 — metadata／標籤編輯應同步重繪時窗時間軸（S4）

對應：**SPEC §6 資料表格與時窗時間軸、§8 S3／S4**。`onDraftInput` 對 metadata 提早 return，只有 start/end 輸入會觸發時間軸重繪。實測把預設 `horizonMin` 從 40 輸入為 80，draft H=80，但 `lastWinEditor.H` 仍 40；第一個拖曳事件會使用舊刻度換算。同樣，需求文字等修改也可能留著舊 canvas 標籤。

> 修改 horizonMin 或時窗列所顯示的 id／sat／station／band／durMin／color 後，只重繪時間軸，不重建正在輸入的表格。H 暫時無效時停用拖曳並提示，重新有效後再繪製；不得沿用舊 H 做新 draft 的座標換算。
