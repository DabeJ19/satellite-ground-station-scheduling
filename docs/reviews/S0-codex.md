### A. MILP 正確性（SPEC §1、§4.1）

| 檢查 | 明確結論 |
|---|---|
| 五條限制與隱含時窗 | 在 B3 的正整數時長、非負校準、合法時窗前提下，三組限制加 S(r,a) 足夠；每需求至多一次另提供必要的結構限制。 |
| 校準是否漏掉正在進行的任務 | 沒有。延長占用區間會排除所有交疊，不只排除開始事件，證明如下。 |
| PPT 實例最大任務數 | 確為 5。但 §1.3 聲稱 R4 與 R6 不能共存是錯誤的，須修正上界證明（B1）。 |
| ε 不翻轉主目標 | 在 B2、B3 明定的等待與資料邊界下成立，推導如下；目前 earliest_r 未定義，規格尚不能無條件宣稱一致。 |
| 半開區間 | 兩組資源限制使用 `t ≤ τ < end`，一致。每需求限制不涉及端點；S(r,a) 必須接受 `t+d_r == window.end`。 |

**校準等價性。** 同天線兩任務 i、j，設 `t_i ≤ t_j`、`d_i,d_j ≥ 1`、`c_a ≥ 0`。天線列把兩者區間設為 `[t_i,t_i+d_i+c_a)`、`[t_j,t_j+d_j+c_a)`。若 `t_j < t_i+d_i+c_a`，在整數列 `τ=t_j` 兩個 x 同時被計入，違反容量 1；否則恰有 `t_i+d_i+c_a ≤ t_j`，滿足校準間隔。因此校準內不能開始另一任務，亦不能存在另一個正在進行的任務。若另一任務更早開始，交換 i、j 即回到同一證明。

衛星只占用通訊區間 `[t,t+d_r)`，不占用校準。因此同衛星可在一支天線校準時使用另一支天線，符合題目。`c_a=0` 時前一任務 end 等於後一任務 start 可行；`c_a>0` 時必須等到 end+c_a。最後一筆校準可以超過 H：只要所有通訊在 `[0,H)`，H 以後沒有新任務可與它衝突，無須強迫 `t+d_r+c_a ≤ H`。若要展示完整校準尾端，畫面可延伸或裁切，但不得因此刪除合法候選。

**手動驗證 Z=5。** 以下排程同時給出較好的次目標，時間為 10:00 起算：

| 需求 | 衛星 | 天線 | 通訊 `[start,end)` | 校準 `[end,end+10)` | 等待 `start-request.start` |
|---|---|---|---|---|---:|
| R1 | SAT_A | GS_1-S | 10:00–10:05 | 10:05–10:15 | 0 |
| R2 | SAT_A | GS_2-X | 10:05–10:07 | 10:07–10:17 | 3 |
| R3 | SAT_B | GS_2-S | 10:08–10:13 | 10:13–10:23 | 2 |
| R6 | SAT_C | GS_2-X | 10:22–10:24 | 10:24–10:34 | 2 |
| R5 | SAT_C | GS_1-S | 10:24–10:29 | 10:29–10:39 | 4 |

每筆均落在需求時窗與相應站的可見時窗中、頻段相容。SAT_A 在 10:05、SAT_C 在 10:24 恰好銜接，半開區間不衝突。每支天線的校準也滿足。故 Z≥5。R2、R4 共用唯一 X 天線：R2 最早 10:03、最晚 10:06 起始，最早完成加校準是 10:15；R4 最晚 10:14 起始，故 R2 不能排在 R4 前。R4 最早 10:08 起始、完成加校準是 10:20，也不可能排在 R2 前。故 R2、R4 至多取一筆；總共六需求，Z≤5，合得 Z*=5。

審查方依 JSON 列舉每需求的「不排入」及全部 `(antenna,start)`，用成對資源區間判斷可行性：可行排程共 3,242 個（含空解），其中 78 個有五任務；五任務最小總等待為 **11**，即上表，`objective=5−11/241≈4.9543568465`。五任務使用 R2+R6 的最小等待為 11；使用 R4+R6 為 14。這是獨立列舉結果，非 glpk.js 實作驗證。SPEC 原範例亦可行且 Z=5，但等待為 15，不能當作完整加權目標的最佳解。

**ε 推導。** 設 `n=|R|`、`H≥1`，已排任務 `0≤wait_r≤H`，未排任務不計等待，故 `0≤W≤nH`。對任意兩可行解 A、B，若 `N_A≥N_B+1`，則

```text
F_A − F_B = (N_A−N_B) − (W_A−W_B)/(nH+1)
           ≥ 1 − nH/(nH+1)
           = 1/(nH+1) > 0.
```

同任務數時，F 大小恰等於 W 的反向排序。空需求集 n=0 時令 W=N=0、ε=1，直接回傳空解。這是精確算術的保證；GLPK 是浮點運算，極大 nH 時不應把數值容差視為同一個證明，須回報整數化的 N、W 並驗證。

### B. GA 設計（SPEC §5）

**間接編碼不會系統性排除最佳解，無須為正確性新增「起始偏移」基因。** 前提是解碼器確實遍歷整個候選集合、可以插入既有排程的空隙，且沒有規格外的只能向後排、額外先後順序、序列相依校準等限制。

證明：取任一「先最大任務數、再最小總等待」的最佳排程 S*。把其中已排需求放在排列 π 的前段，按 S* 起始時間遞增排序（同時開始任意排序），未排需求放後段；每需求天線偏好設為其 S* 的天線。

依序解碼時，先前任務的開始、結束及校準結束皆不晚於原排程，故當前任務的原開始時間仍可行；解碼器一定能在偏好天線找到不晚於原開始的時間。若它嚴格提早，對已排任務由檢查器保證可行；尚未排但原本較晚開始、且共享資源的任務，其原開始均不早於當前任務原占用結束，當前任務提早不會對它新增衝突。於是得到任務數相同、總等待更小的全排程，與 S* 的次目標最佳性矛盾。因此所有已排任務都能重建；後段再插入任何未排需求則會增加任務數，與主目標最佳性矛盾。故至少有染色體可表示最佳解，實際上可按上述方式重建每個加權最佳排程。

這是搜尋空間覆蓋性，**不保證有限族群與世代會找到它**。審查方另列舉預設資料的 6!×2³=5,760 種排列與相容 S 天線首選：能排 3/4/5 筆者分別為 1,328/2,944/1,488，其中 372 種達 `(5,11)`，與獨立最佳值一致。此列舉亦不是 ga.js 的測試。

**直接修復與間接編碼的可行 phenotype 可直接比較。** 兩者都須對最終排程呼叫同一 `score()`；直接模式不能拿修復前染色體的分數比較。不同修復順序會改變結果與搜尋難度，並不改變同一排程的分數。罰則模式的 raw fitness 在有違規時不能和 MILP objective 當成同一個最佳化品質指標（S2）。

**總等待的完全一致性目前尚未規定完整。** MILP 係數與 GA 均提到 objective，但 earliest_r 的來源、未排需求的等待未定義；須依 B2 統一。若一方使用需求 start、另一方使用最早可見時刻，即使同一排程也會有不同分數。

## 阻擋項（必修）

### B1 — §1.3 上界證明含錯誤不相容關係（SPEC §1.3、§8）

反例：GS_2-X 上 R4 `10:08–10:10`，校準至 `10:20`，接 R6 `10:22–10:24` 完全可行。因此「R4 與 R2、R6 任一皆無法共存」是錯誤敘述。Z≤5 的結論能保留，證明改用 R2/R4 互斥。

**可直接採用的修改文字：**

> 三筆 X 需求共用唯一 X 天線。R2 的可行起始為 10:03–10:06，R4 為 10:08–10:14（皆為整數分鐘且範圍含兩端）。若先做 R2，最早完成加校準是 10:15，已晚於 R4 最晚起始 10:14；反向順序亦不可能。因此 R2、R4 至多排一筆，X 任務至多兩筆，總任務數至多五。R4 與 R6 可以共存。五任務可行排程例如 R1/GS_1-S/10:00、R2/GS_2-X/10:05、R3/GS_2-S/10:08、R6/GS_2-X/10:22、R5/GS_1-S/10:24，故最佳 Z=5。依 §1.1 的需求 start 基準，其總等待為 11 分鐘，為加權最佳解。原範例亦達 Z=5，但總等待為 15。

驗證：上文給出手算資源與時窗核對，獨立全列舉確認 `(Z,W)=(5,11)`。

### B2 — 等待基準與未排需求貢獻未定義（SPEC §1.1、§3、§4.1、§5.1）

`earliest_r` 沒有對應欄位或函式定義。預設 R2 的需求 start=2、全域最早可行起始=3，兩種理解已會產生不同結果；不能等實作方各自選。這會影響不同選取集合的排名，並非單純顯示差異。

**可直接採用的修改文字：**

> `earliest_r := requests[r].start`，為需求允許開始的下界，不是目前部分排程中可插入的最早時間，也不隨所選天線改變。只對已排需求計算 `wait_r = schedule.start − earliest_r`；未排需求貢獻 0。`assigned` 為已排的不同需求數，`totalWait` 為上述等待總和，`objective = assigned − totalWait/(|R|·H+1)`。MILP 係數與所有 GA 模式一律使用 engine 匯出的同一定義。正式可行解比較使用 `(assigned 降序, totalWait 升序)`，與該加權目標數學等價。空解分數為 `(0,0,0)`。

驗證：以同一份 Schedule 分別經 MILP 結果轉換與兩 GA 模式評分，三個欄位須相同；上表應為 `(5,11,5−11/241)`。若 PO 想選最早可見時刻作基準，須另明文拍板並重算驗收，不能混用。

### B3 — 輸入與 Schedule 的合法域未封閉（SPEC §2、§3、§4.1）

可增刪／JSON 匯入卻沒有資料驗證契約。負校準破壞天線等價證明，負起始或越出 H 的時窗破壞 ε 的界；重複需求排在不同時間也不一定違反既有五條規則，但會違反 MILP 的每需求至多一次，造成手動／GA 與 MILP 的可行域不一致。時長固定由需求衍生是合理的，不需在 Schedule 新增可編輯 duration。

**可直接採用的修改文字：**

> 在求解／匯入／資料編輯提交前執行 `validateData()`：H 為正整數；需求時長為正整數；全域及天線校準為非負整數；所有需求／visibility 的 start/end 為整數且 `0 ≤ start < end ≤ H`。衛星、站、需求 id 各自唯一，天線 id 全資料唯一；引用的衛星、站、band 必須存在。資料不合法時保留錯誤位置並停止求解，不靜默截斷或修正。需求時長大於可用時窗、或沒有相容天線／可見時窗時，S(r,a) 可為空，該需求不排入，不是整體模型不可行。
>
> 天線 `calibMin` 缺省或 null 時採 `calibDefaultMin`，0 是有效覆寫，使用 nullish fallback。每 `(sat,station)` 的 visibility 先排序，將重疊或相鄰片段合併為連通區間。S(r,a) 包含所有整數 t，使 `[t,t+d_r)` 落在 `[0,H)`、需求單一時窗、以及一段正規化 visibility 的交集中，且頻段相容；合併前不得漏掉跨相鄰片段的完整通訊。
>
> `checkFeasible()` 除資源規則外，必須拒絕未知 req／antenna、重複 req、非整數 start、非法引用及超界時間；新增結構錯誤碼 `'schema'`、`'duplicate-request'`。任務 end 一律由 `start+durMin` 衍生，不信任匯入的 duration/end。MILP、GA、手動及 worker 均使用相同候選、占用區間與檢查核心；MILP 線性限制是該核心語意的轉譯，輸出仍須驗證。
>
> 初始天線均視為在 t=0 可用；最後校準可跨 H，只有通訊需要完整落在需求及可見時窗內。

驗證：至少涵蓋 calibMin=0、負校準、重複 req、`end==window.end`、相鄰 visibility 合併、H 尾端通訊合法但校準跨 H，以及無候選需求的空解。

### B4 — 超時後 LP 上界與 gap 缺少有效性條件（SPEC §4.2、§6）

「另跑一次無整數限制取得 bound」只有在 LP 求到最佳、或取得已驗證的對偶可行上界時才成立。最大化 LP 的一般可行解 objective 是下界，若 LP 自己超時，不能把其 incumbent 當上界。規格也未說明 gap 對應任務數還是加權 objective，或第二次求解是否仍受時間預算限制。

**可直接採用的修改文字：**

> 定義 L 為經 `checkFeasible()` 通過之整數排程的加權 objective。LP 鬆弛沿用同一目標與全部列，變數改為連續 `0 ≤ x ≤ 1`（顯式 bounds，移除 binaries/generals）；只有 LP 狀態 `GLP_OPT` 才把其 objective 記為 U。LP 的 `GLP_FEAS`、`UNDEF` 或失敗均不提供 U；沒有有效 U 時顯示「上界／gap 尚未取得」，不得以 LP 可行目標值冒充上界。
>
> 有 U 時顯示 `absoluteGap=max(0,U−L)`，`relativeGap=absoluteGap/max(1,abs(L))`，標示「加權目標的 LP 鬆弛 gap，非原生 B&B gap，亦非任務數差距」。比較時容許小幅浮點誤差；若 U 顯著小於 L，回報計算錯誤，不以截成 0 掩蓋。
>
> 使用者秒數是 MILP 與額外 LP 共用的求解預算，記錄各自耗時；沒有剩餘時間就不啟動 LP，並提供中斷／worker 終止機制。`GLP_FEAS` 標「有可行解，未證明最佳」，僅於確知原因時加註超時；`GLP_OPT` 才標「已證明最佳」。無 incumbent 時不得把空值解碼成結果。合法資料允許所有需求不排入，因此空排程必可行；`GLP_NOFEAS` 應提示模型／數值異常待診斷，而非宣稱使用者需求必須全部能排入。

GLPK JSON API 的 bounds 與整數類型是不同欄位，見 [glpk.js 官方 API](https://github.com/jvail/glpk.js#api)。即使每需求列與非負界已隱含單變數上界，顯式 0..1 仍可避免轉換歧義。

目前「greedy Z=4」缺順序／天線首選，「不可行解報 4 條」缺輸入 Schedule 與違規計數定義；只寫數量無法區別重複報錯與漏報。原 PPT 待工程方補原始頁碼／資料對照，不由本報告猜填。

**可直接採用的修改文字：**

> S1 固定 greedy order=`[R1,R2,R3,R4,R5,R6]`，相容天線依資料列出順序嘗試，S 頻段首選 GS_1-S，X 首選 GS_2-X。預期 R1/GS_1-S/0、R2/GS_2-X/5、R3/GS_2-S/8、R5/GS_1-S/20，Z=4、等待=5。另收錄原 PPT 不可行 Schedule 的完整 JSON、來源頁碼及預期 `(rule,reqs)` 集合；資源衝突依需求對與規則去重，不按重疊分鐘重複計數。MILP 另驗收 Z=5、等待=11，不能只比加權小數或特定天線選擇。

### S2 — 固定解碼、修復與比較對象（SPEC §3、§5.1、§6）

最早可行解碼的覆蓋證明依賴完整空隙插入。修復／罰則 raw fitness 與正式排程評分應有清楚分工；§3「都必須通過才顯示」與 PO 已允許的手動不可行展示也需對齊。

**可直接採用的修改文字：**

> 間接解碼對每支被嘗試的天線，從其完整 feasibleStarts 由小到大掃描，可插入已排任務之前及空隙，不以全域游標或最後任務末端作為起始下界。不因正確性需求增加偏移基因。直接修復依 requests 陣列順序處理，未通過者從 phenotype 移除；fitness 使用修復後 Schedule 的 engine.score。罰則模式另存 rawFitness、違規與最佳可行解。三解槽評分卡一律回報 assigned、totalWait、objective、feasible；不可行排程可標紅顯示與播放，但不得計入最佳可行解、MILP 命中率或最優性比較。MILP 轉出的不可行結果視為錯誤，不當成正常解槽成果。

### S3 — 完整 state、worker 與離線驗收（SPEC §2、§3、§5、§7、§8）

目前 IIFE 以 `window.SGS` 為入口，GA worker 沒有 window；共用核心不能只是主頁面有載入。Blob/CSP、儲存被拒、非同步結果遇上資料編輯也需明確處理。

**可直接採用的修改文字：**

> 共用引擎以 globalThis.SGS／純函式掛載，同一份原始碼同時內嵌到主頁及 GA Blob worker，不在 worker 重寫規則。Blob worker 腳本自足，不使用外部 import 或 wasm fetch；若日後設定 CSP，允許所需 blob worker 與 wasm 執行。worker 與主頁交換資料快照及 revision/runId；資料改動或取消後的舊結果不覆蓋目前解槽。所有 localStorage 存取皆捕捉失敗，降級記憶體使用並提示 JSON 匯出備份。單檔離線驗收記錄 Chrome／Edge 版本、file://、斷網、GLP_OPT 且 z=3、GA worker 啟動／取消及無外部請求；儲存失敗不得阻止排程操作。

依據：[MDN Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers) 說明 worker 全域、訊息資料複製及 Blob 的 CSP 繼承。

### S4 — 強化 vendor export 轉換與內嵌完整性（SPEC §7、build.js）

現有 `includes` 加單次 replace 不能確認唯一尾端，亦綁定 pe。固定版可先留用；升級時應避免猜測另一個壓縮符號。原始 JSON 直接插進 script，未來名稱若含 `</script>` 亦會截斷內嵌。

**可直接採用的修改文字：**

> build 對固定 glpk 版本驗證 SHA-256，確認預期 export 恰好一次且為合法檔尾，任何不符立即失敗。將目前轉換封裝為具 fixture 的版本專用 adapter；升級時優先使用 AST parser／bundler 由模組入口在記憶體產出 IIFE，避免依賴壓縮私有名稱，仍不改寫 vendor/。所有 inline 標記必須恰好出現一次並完全替換。預設資料先 JSON.parse 驗證，再 JSON.stringify 並將 `<` 等 script 敏感字元轉義；檢查內嵌 JS／CSS 的 HTML 結束標記不會提前關閉元素。煙霧測試成功條件同時包含 z=3 與 status=GLP_OPT。

### S5 — 最小協作規則仍須寫入（SPEC §7、§8；AGENTS.md 儲存庫與同步）

不需建立額外多 agent 治理系統，只補明確寫入邊界與版本對齊。

**可直接採用的修改文字：**

> Codex 僅可在 review/<sprint> 新增該輪 docs/reviews/<sprint>-codex.md，不修改工程檔或 main。送審包與報告均記錄被審 commit SHA；工程方合併 review PR 前核對是否已改動被審內容，若有須列差異或重新送審，不能將舊 review 當作新版本通過。工作開始先 fetch 並確認分支／工作目錄狀態；不得覆蓋對方未提交變更、reset 他人分支或 force push。既有 review 檔不得靜默重寫，複審另約定檔名。SPEC 修訂仍由工程方依既有規則追加 DECISIONS 紀錄。

### S6 — 多次 GA 統計與命中定義（SPEC §5.2、§5.3、§8）

`同 seed 同結果` 未說明多次 run 如何取得不同亂數流；「PPT 第一代即達最佳」也不是保證。MILP 未證明最佳時，不能把命中 incumbent 稱為命中最佳。

**可直接採用的修改文字：**

> 多次 run 使用明確可重現的不同 run seed（例如 `(baseSeed+i) >>> 0`），匯出每次 seed、資料／參數版本、停止原因及 assigned/totalWait。所有隨機算子只用指定 PRNG，不用 Math.random；正式重現驗收按世代／停滯停止，不以實際牆鐘時間決定。分別報「命中主目標 Z*」與「命中完整最佳 (Z*,W*)」，只有相同資料且 MILP 已證明最佳才使用最佳命中率名稱。未證明時改報對 incumbent 的差距。平均達最佳世代數僅對命中 runs 計算，未命中數另列；指定標準差採樣本或母體定義。PPT 20 runs 100% 是固定 seeds 與預設參數的經驗驗收，非任意 seed／第一代必中的演算法保證。

### S7 — 保留依賴決策，補單檔授權交付（SPEC §4、§7、§8）

上游明示 GPL-3.0，頁尾簡稱不能代替完整授權資訊。這不要求更換 solver，也不要求推翻 PO 決策；僅需讓離線交付物的說明與實際組成一致。上游依據：[glpk.js LICENSE](https://github.com/jvail/glpk.js/blob/master/LICENSE)。

**可直接採用的修改文字：**

> S4 的單檔 HTML 內保留 glpk.js 的版權與 GPL-3.0 授權全文／聲明，並提供所用確切版本、建置轉換說明及對應來源取得方式。README 區分自有程式授權與內嵌依賴授權，不把整份含 glpk.js 的 HTML 表述為純 MIT。離線發送 HTML 時一併核對授權文字和對應來源交付方式，不能僅因課堂用途而略過。

## 針對 SPEC 開放問題的意見

### 1. 事件點限制（SPEC §9.1、§4.1）

**建議：S1 保留逐分鐘；依候選變數數、非零係數數與實測時間決定最佳化，不以 H>1440 單獨切換。** 若壓縮限制列，必須用所有「候選占用區間」的事件，不能只用輸入 visibility 的起訖。天線事件由候選 `[t,t+d_r+c_a)` 導出，衛星事件由 `[t,t+d_r)` 導出。實際只保留每個資源的所有候選 start 時刻已足夠：任一超載區間取其中最新開始的任務，其開始時刻必可見同一超載；完整起訖端點法亦可，半開區間同時刻先處理結束再處理開始。候選每分鐘都有時，事件點未必省列，更不會自動減少變數。

**可直接採用的修改文字：**

> S1 使用每分鐘列；另記錄候選數、列數、非零係數數、建模及求解時間。後續僅在有實測收益時，以每資源所有候選占用區間的起始事件建立等價容量列，並與逐分鐘模型比對可行域及最佳 (Z,W)。不得只以 visibility 邊界或某一個已選排程作事件點。

### 2. 動畫相位擬合殘差（SPEC §9.2、§6）

**建議：接受，沿用 PO 已決策的示意動畫；不把擬合幾何用於判斷可見性或排程。** 角度應採圓周距離，避免 359° 與 1° 被算成 358° 誤差；需明定 ω 才能重現。

**可直接採用的修改文字：**

> 動畫標示「軌道為示意，接觸狀態以輸入時窗為準」。固定預設 `ω=360/H` 度／分鐘（僅視覺參數），以圓周角距離平方和擬合 φ；沒有可見時窗時按衛星索引等距初始化 φ，退化或多解時取規定的最小角度。顯示或記錄擬合殘差即可，不把殘差當排程違規。

### 3. 直接編碼罰則 λ（SPEC §9.3、§5.1）

**建議：預設 `λ=|R|+1`，每次資料變更重新計算，仍保留可調參數。** 前提是已用 B3 限定每需求至多一個基因、起始非負且等待非負；結構非法者先拒絕／正規化，不能讓重複需求或負起始灌高分數。令 V 為共用檢查器回報、依 `(rule,reqs)` 去重的違規數，任何不可行者 V≥1。基礎 F≤n，因此不可行者 `F−λV≤n−(n+1)=−1`，低於可行空解 0；可行者 V=0，分數與 MILP／間接編碼相同。這是可行優先的保守預設，並不保證 GA 收斂；使用者調低 λ 後不再有此保證。

**可直接採用的修改文字：**

> λ 預設為 n+1，fitness=`score.objective−λ·V`。V 使用 engine 的違規集合，每個 `(rule,reqs)` 計一次，不按分鐘累計；λ 改動只影響搜尋，不改正式評分。保留最佳可行解並以空排程作保底，另可展示當代不可行個體及其違規。不可行者不列入最佳可行命中統計。結構非法染色體先處理，再計分；使用者降低 λ 時標明不再保證可行解優先。
